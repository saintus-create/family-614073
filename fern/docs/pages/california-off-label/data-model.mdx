## Why structured data comes first

The provider should enter a clinical fact once. That fact should then be reusable across the evidence dossier, consent checklist, prescribing record, monitoring plan, and coverage packet.

The site therefore treats the prescribing record as structured data rather than as a form that produces an isolated block of prose.

## Authority status is explicit

Every legal or regulatory item will eventually be classified as one of four things:

| Status | Meaning |
| --- | --- |
| Mandatory | A binding requirement applicable to the particular situation. |
| Permissive | Authority that permits an action without itself imposing the action as a requirement. |
| Advisory | Guidance or professional recommendation that is not itself a statutory command. |
| Evidentiary | Material that may support a clinical, regulatory, or coverage proposition but does not itself create an obligation. |

This prevents the application from turning a clinical guideline into a statute or turning an evidentiary source into a legal command.

## Provenance is part of the record

The production system should retain the exact source used, the jurisdiction, effective date where applicable, applicability conditions, and verification timestamp. If an authority changes, the system should be able to distinguish the version relied upon when the record was created from the authority currently in force.

## Implementation target

The schema is stored at `fern/data/off_label_record.schema.json`. It is deliberately conservative at this stage. The next layer can add enumerations, validation rules, authority relationships, evidence scoring, and machine-readable applicability conditions without changing the provider-facing workflow.
